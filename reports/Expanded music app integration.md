# Build BitChord into our complete player

Research and implementation planning · 16 November 2026

**Keep the complete BitChord application as our base, add our native Audio Lab and StaaaaandBy display, then port selected capabilities from LastWave, Metrolist and Cubic.** The additional projects materially improve the available feature set: headphone profiles, metadata editing, safer imports and backups, recoverable downloads, protected lyrics edits, listening recaps and widgets. They do not justify another change of visual direction. The user has explicitly chosen BitChord's actual UI, animations and playback experience; this plan supersedes the earlier proposal to reconstruct those screens around the old workstation shell. “Implement everything” becomes a combined feature roadmap, with one owner for each shared concern rather than several competing players, databases and settings systems. Source reuse is the default where a bounded component fits; adapters connect that code to BitChord. The first delivery remains the real BitChord build with one demonstrably working native effect, followed by manual Dock Mode.

## Preserve the actual BitChord experience throughout

BitChord already carries substantial playback, source, queue, artwork, lyrics and offline machinery. Its `PlaybackService` owns player construction and custom sink integration, while its shared UI contains the actual player and lyrics implementation. Keeping that complete application preserves the visual and behavioral work the user wants. An Audio Lab entry and a Dock action should extend its player/settings flow; importing another home screen or rebuilding its navigation would repeat the rejected approach. ([BitChord playback owner](<D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/PlaybackService.kt:312>), [sink construction](<D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/PlaybackService.kt:6832>), [existing player UI](<D:/MusicPlayer-Projects/BitChord/sharedUi/src/jvmSharedMain/kotlin/com/music/bitchord/ui/player/NowPlayingScreen.kt>))

“One playback authority” means one owner of the session, queue, source decisions and lifecycle. It does not require deleting BitChord's managed secondary player used for transitions. The new components consume that owner's state. Audio Lab processes eligible PCM; dock and widgets display and control the same session; imports update the destination library; history records the same playback events. Donor services should not independently start audio, choose the next song or publish a competing now-playing state. BitChord's queue-generation rules already provide a useful boundary for rejecting stale asynchronous work. ([Queue edit coordination](<D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/BoundedQueueEdits.kt:11>))

The implementation state is limited and explicit. The earlier partial UI port is preserved on `codex/bitchord-ui-port`. A separate `codex/bitchord-base` branch imports the complete 1,409-file BitChord snapshot into `bitchord/`; its source manifest records that import. **The full-base build has not yet been established:** the initial Gradle 8.11.1 download timed out during bootstrap. Android platform/build-tool setup was fetched, but that is not a passing application build. No native Audio Lab effect is connected to this new base yet. The expanded donor review performed no donor builds, installs or runtime tests and changed research files only. ([Import manifest](<C:/Users/SDK/.codex/worktrees/1faa/Music Player/docs/porting/bitchord-base-import.json>), [pinned wrapper](<C:/Users/SDK/.codex/worktrees/1faa/Music Player/bitchord/gradle/wrapper/gradle-wrapper.properties>))

## Each donor contributes a distinct part of the product

The new folders contain substantial applications, not self-contained plug-ins. LastWave combines Android data layers with its own native/player stack. Metrolist separates Android and multiplatform modules and brings a large versioned database. Cubic retains active RiMusic/Kreate package families and its own playback/database paths. These observations establish different integration shapes; a common parent folder, shared dependencies or import support does not prove that the three are interchangeable forks. ## Reuse code through clear boundaries and preserve its meaning

**Audio Lab needs a dedicated integration boundary, not another running player.** BitChord's ordinary DSP chain processes Float32 blocks; LastWave's native PCM processor also produces Float32, and Metrolist's Android EQ explicitly bypasses non-PCM16 input. None supplies our required full Float64 processing path by being copied. The existing native code also needs an audited precision boundary before the combined app advertises that property. Establish where original decoder PCM enters, how enabled processing promotes it, what format leaves, and how all-off bypass avoids unnecessary conversion. Keep routing, decoding changes and emulation improvements separate from the first bridge. ([BitChord DSP](<D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/DspChain.kt:34>), [LastWave PCM boundary](<C:/Users/SDK/Downloads/Cubic-Music-main/LastWave-Native-main/app/src/main/java/com/lastwave/app/playback/NativePcmAudioProcessor.kt:95>), [Metrolist encoding gate](<C:/Users/SDK/Downloads/Cubic-Music-main/Metrolist-main/androidApp/src/main/kotlin/com/metrolist/android/playback/EqualizerAudioProcessor.kt:42>), [our current DSP interface](<C:/Users/SDK/.codex/worktrees/1faa/Music Player/src/app/src/main/cpp/dsp/DspChain.hpp:244>))

The first effect should have a small measurable contract: configure off the processing thread, process preallocated buffers, reset correctly on seek/format change, and bypass deterministically. Native controls must not enable duplicate BitChord EQ, gain or limiting stages. The UI should report which processor is active and which output format is actually known. Crossfade, speed changes and active effects change samples; an “Original” mode must account for all relevant processing rather than merely one Audio Lab switch. Actual DSP order, USB feedback behavior and real-time safety remain subject to the existing engine gates.

**Dock is a presentation client of the same session.** StaaaaandBy already separates artwork/clock drawing from a WebView renderer fed song, color and playback anchors. Reuse those display pieces with BitChord's existing artwork and lyrics. Start manually, with visible controls and exit; later evaluate charging/screensaver integration. Its external-app notification watcher, stale Spotify mirror heuristics and separate charging service solve a different problem and are unnecessary for displaying our own playback. Native lyrics remain the accessible fallback when the animated page is unavailable or disabled. ([Dock drawing](<D:/MusicPlayer-Projects/StaaaaandBy/app/src/main/java/com/kazuto/standby/ui/StandbyScreen.kt:388>), [WebView contract](<D:/MusicPlayer-Projects/StaaaaandBy/app/src/main/java/com/kazuto/standby/ui/LyricVideo.kt:33>))

For library features, use neutral imported-track, playlist, lyric-document, profile and history records at donor boundaries. Preserve destination IDs, release/source identity and ordered playlist occurrences. A source account's song ID, a local URI and an expiring download URL are not interchangeable identities. Preview imports before applying them, distinguish exact/probable/ambiguous/missing matches, and preserve the unresolved entries rather than silently replacing them with a different recording. Metrolist's foreign-library importer is useful source parsing, but its DAO/resource dependencies need adapters; Cubic's CSV model can preserve source metadata without importing its service. ([Foreign import implementation](<C:/Users/SDK/Downloads/Cubic-Music-main/Metrolist-main/shared/src/commonMain/kotlin/com/metrolist/shared/backup/ForeignLibraryImport.kt:42>), [CSV model](<C:/Users/SDK/Downloads/Cubic-Music-main/Cubic-Music-main/composeApp/src/androidMain/kotlin/app/kreate/android/me/knighthat/utils/csv/SongCSV.kt:8>))

Lyrics should retain plain, line and real word timing as distinct capabilities. Port draft/protection rules so a provider response cannot overwrite a user edit, and invalidate stale asynchronous results after track or revision changes. Cubic contains a proportional-progress fallback when word timestamps are absent; that is an animation approximation, not measured word synchronization. Share one lyric document and anchored playback clock between BitChord's normal reader and dock. ([Metrolist selection policy](<C:/Users/SDK/Downloads/Cubic-Music-main/Metrolist-main/shared/src/commonMain/kotlin/com/metrolist/shared/repository/LyricsRepository.kt:99>), [Cubic editor](<C:/Users/SDK/Downloads/Cubic-Music-main/Cubic-Music-main/composeApp/src/androidMain/kotlin/app/it/fast4x/rimusic/ui/screens/player/Lyrics.kt:1290>), [timing fallback](<C:/Users/SDK/Downloads/Cubic-Music-main/Cubic-Music-main/composeApp/src/androidMain/kotlin/app/it/fast4x/rimusic/ui/screens/player/Lyrics.kt:342>))

The useful product combination is a familiar BitChord app that also remembers what the user needs: a selected headphone profile in Audio Lab, an offline collection with separate audio/art/lyric readiness, editable lyrics that survive provider refreshes, a backup that restores ordered playlists, and a listening recap based on real history. These are proposed experiences over shared state, not additional app shells.

The order keeps the user's requested Audio Lab and standby experience visible early while preventing later import and persistence work from scattering state. Each selected donor feature begins with a short gap comparison against the exact BitChord snapshot: identify what is missing, retain existing equivalents, then copy only the code needed for the improvement. This is still code reuse, not a mandate to rewrite every implementation. Calendar estimates should follow the baseline build and first native-bridge spike, when dependency closure and PCM behavior are measurable.

## Resolve donor-specific risks before exposing features

Whole-module import carries avoidable dependencies. Metrolist's snapshot declares a newer Room3/KMP/toolchain graph, and its `metroproto` submodule directory is empty in the supplied copy. Cubic has separate Android/common database paths and declared desktop dependencies. Those are reasons to extract bounded implementations and their tests; they are not evidence that either snapshot fails to compile. **The new donors were not built in this review.** ([Metrolist declared toolchain](<C:/Users/SDK/Downloads/Cubic-Music-main/Metrolist-main/gradle/libs.versions.toml:2>), [submodules](<C:/Users/SDK/Downloads/Cubic-Music-main/Metrolist-main/.gitmodules:1>), [Cubic build separation](<C:/Users/SDK/Downloads/Cubic-Music-main/Cubic-Music-main/composeApp/build.gradle.kts:64>))

Cubic's recognition repository references `ShazamSignature`, but its declaration or explicit generator/dependency closure was not found in the inspected snapshot; bundled fingerprint `.so` files alone do not resolve that source question. A corruption-view helper was also found at call sites without a located implementation. Treat those features as conditional investigations, not completed recognition/integrity modules. If recognition becomes a priority, compare the donors with the official Android ShazamKit route before choosing one provider boundary. ([Recognition reference](<C:/Users/SDK/Downloads/Cubic-Music-main/Cubic-Music-main/composeApp/src/androidMain/kotlin/app/it/fast4x/rimusic/recognition/ShazamRepository.kt:37>), [validator call](<C:/Users/SDK/Downloads/Cubic-Music-main/Cubic-Music-main/composeApp/src/androidMain/kotlin/app/kreate/android/themed/rimusic/screen/home/HomeSongs.kt:237>), [official ShazamKit Android API](https://developer.apple.com/shazamkit/android/shazamkit/com.shazam.shazamkit/-shazam-kit/index.html))

Recovery and privacy need separate tests. LastWave's manual backup export filters named credentials, but its platform backup exclusions are a different mechanism. Metrolist offers Keystore-backed migration patterns, but restored encrypted data still needs handling when the original key is unavailable. Diagnostics should redact tokens, cookies, signed URLs and private paths before a user reviews an export. Tag editing requires explicit storage grants, staging and recoverable failure behavior. These protections belong in adapters and failure tests, away from audio processing. ([LastWave backup filtering](<C:/Users/SDK/Downloads/Cubic-Music-main/LastWave-Native-main/app/src/main/java/com/lastwave/app/data/backup/BackupRepository.kt:44>), [platform extraction rules](<C:/Users/SDK/Downloads/Cubic-Music-main/LastWave-Native-main/app/src/main/res/xml/data_extraction_rules.xml:1>), [Metrolist secure migration](<C:/Users/SDK/Downloads/Cubic-Music-main/Metrolist-main/shared/src/androidMain/kotlin/com/metrolist/shared/settings/AndroidSecureSettings.kt:23>), [LastWave crash context](<C:/Users/SDK/Downloads/Cubic-Music-main/LastWave-Native-main/app/src/main/java/com/lastwave/app/diagnostics/CrashRecorder.kt:81>))

The user's permission context remains accepted; it does not need another general licensing questionnaire. Record copied files, origins, modifications and notices as each port proceeds. The three new root projects carry GPLv3 notices, while dependencies and assets have their own provenance. AutoEQ's upstream root license is MIT, but its repository aggregates measurements from multiple sources; code permission must not be represented as completed clearance for every measurement or target dataset. Keep per-profile source/rig/target/version information and offer user-supplied profile import while specific data-use questions are resolved. Provider access, lyric content and opaque native assets likewise need their own concrete provenance rather than an app-level assumption. This review inventoried the new projects and traced major candidate modules, contracts, dependencies and representative tests. It did not read every line, audit every dependency, execute donor tests, establish provider uptime or measure their S24+ audio behavior. File presence is evidence of code to inspect and reuse; it is not a passed build, migration or audio-integrity gate. The next coding step is therefore unchanged in purpose: establish the complete BitChord baseline and prove one native effect inside it. The expanded backlog then lets subsequent deliveries add substantial capability while preserving the app the user actually chose.
