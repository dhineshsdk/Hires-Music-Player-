# BitChord source and integration research

## What does BitChord actually contain and which parts are useful?

### Takeaway

BitChord is a large consumer music ecosystem, rather than a reusable hi-res engine module. Its strongest contributions to our product are library organization, lyrics, artwork presentation, queue behavior, download management, sleep controls, and honest source/output status. Keep the existing native engine and re-create the selected experience around it; do not substitute BitChord's entire playback layer.

### Inferences

Recommended first-release feature selection, ordered by value and fit:

1. Library: albums, artists, folders, favorites, ordered playlists, search, recently played and queue restoration.
2. Lyrics: embedded/local LRC, online opt-in provider, line synchronization, seek correction and user timing adjustment; word timing only when real data exists.
3. Artwork and landscape: full-screen owned art, luxury motion treatment, shared dock presentation, reduced-motion mode.
4. Playback conveniences: persistent sleep timer, stop-after-track, repeat/shuffle/play-next/reorder/delete with reliable next-track invalidation.
5. Downloads/source management: supported user files, staged writes, quality/permission/capability reporting and durable resume.
6. Optional later: NAS, scrobbling, stats, playlist imports, companion devices, casting, group listening and DJ transitions.

Creative product ideas (proposals, not present functionality): an **Album Room** dock view combining sleeve/record identity, warm clock, synchronized lyrics and verified output format; an **Edition Shelf** showing multiple masterings/source variants without silently swapping them; a **Travel Crate** that prefetches a selected album/playlist with exact byte estimate and verification status; and **quiet listening** controls that pair sleep-after-track with a dim dock clock while leaving sample processing untouched. Keep all as affordances inside the existing five tabs, sheets and full-screen modes.

### Gaps

- This is a broad static source review of representative feature implementations, contracts, entry points and tests, not a line-by-line audit of all 1,409 files or a proof that every provider works today.
- No build, unit test, emulator, S24+ benchmark, packet capture, DAC null test or online login was run, per plan-only scope. Source existence is not a shipping-quality guarantee.
- No full third-party artwork, lyric-provider or ONNX-weight rights audit was performed. A class comment asserting permissive weights is not sufficient release evidence.

## What conflicts with our audio architecture or release constraints?

### Takeaway

BitChord's audio code contains useful failure-handling and truthfulness ideas, but its Float32 pipeline, transition system, USB limitations and blocking/exceptions-based transport conflict with the supplied audio-engine rules. This supports feature-level integration while retaining our native engine.

### Cited Findings

- DSP is in-place **Float32**, ordered spatial → equalizer → transition filter → loudness/limiter. The debug processing path logs periodically. [DSP chain](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/DspChain.kt:10), [actual calls](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/DspChain.kt:57). This differs from the user's native Float64/fixed-order architecture; do not import it into the real-time process path.
- Bit-perfect routing sits in front of its ordinary DSP/Media3 sink and bypasses that chain for acceptable tracks. Output exactness and fallback reasons are explicit model fields. [sink construction](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/PlaybackService.kt:6879), [status](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/bitperfect/BitPerfectOutput.kt:65).
- Android14 MixerTransport checks actual route and preferred mixer attributes, including a periodic 250 ms verification and listeners; AudioTrack remains unity volume. [mixer transport](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/bitperfect/MixerTransport.kt:26), [verification](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/bitperfect/MixerTransport.kt:130). This is worth incorporating as a requirement for honest output status, independently of implementation reuse.
- USB descriptor planning explicitly rejects implicit feedback, ambiguous clock selectors and multiple configurations; only a limited mono/stereo UAC path is accepted. [parser constraints](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/bitperfect/usb/UsbDescriptors.kt:19), [implicit rejection](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/bitperfect/usb/UsbDescriptors.kt:281). A unit test explicitly expects this rejection. [test](D:/MusicPlayer-Projects/BitChord/app/src/test/java/com/music/bitchord/playback/audio/bitperfect/usb/UsbAudioLogicTest.kt:104). Our required implicit-feedback support therefore remains new work.
- USB worker `Session::run` acquires `std::unique_lock<std::mutex>` each loop, services control requests on the same worker, and uses exceptions for transfer failures. [worker loop](D:/MusicPlayer-Projects/BitChord/app/src/main/cpp/bitperfect/usb_transport.cpp:273), [mutex](D:/MusicPlayer-Projects/BitChord/app/src/main/cpp/bitperfect/usb_transport.cpp:287), [exception handling](D:/MusicPlayer-Projects/BitChord/app/src/main/cpp/bitperfect/usb_transport.cpp:394). This is incompatible with the supplied no-blocking-lock/no-exceptions USB pump rule and separate-control-module direction.
- Native CMake targets use C++17, build analysis, loop mix, DSD decimator, DST, exclusive output and USB separately; Oboe conversion is disabled, loopmix enables fast-math while analysis does not. libusb is built static and linked into the USB shared library. [native build](D:/MusicPlayer-Projects/BitChord/app/src/main/cpp/CMakeLists.txt). Do not inherit these flags/dependencies wholesale into the C++20/no-exceptions core.
- Model-assisted Automix is actual optional code, including Beat This ONNX beat/downbeat tracking, open-unmix vocal detection and native STFT frontends; missing models fall back to no grid. [beat tracker](D:/MusicPlayer-Projects/BitChord/shared/src/jvmSharedMain/kotlin/com/music/bitchord/playback/smart/BeatTracker.kt:36), [vocal tracker](D:/MusicPlayer-Projects/BitChord/shared/src/jvmSharedMain/kotlin/com/music/bitchord/playback/smart/VocalTracker.kt:79), [crossfade wiring](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/PlaybackService.kt:1921). This adds CPU/memory/model lifecycle and pre-analysis work; it is not a small crossfade toggle.
- EncryptedPrefs can fall back to ordinary SharedPreferences if the Keystore is unavailable, though it repairs stale keysets and migrates back when possible. [fallback](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/auth/EncryptedPrefs.kt:46). A commercial release should choose an explicit credential-storage failure policy rather than silently adopting plaintext fallback.
- QuickJS modules use persistent VM pools with network bindings; each module can have three engines and twelve modules may be resident. [executor](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/data/sources/module/QuickJsExecutor.kt:22), [limits](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/data/sources/module/QuickJsExecutor.kt:71). Capability controls, network destination policy, time/memory limits, signature/provenance and Play policy need design before arbitrary downloaded modules become a product feature.
- BitChord SpotifyLibrary talks to the web player's partner GraphQL endpoint with web bearer/client tokens; this is not a straightforward official Web API integration. [Spotify library](D:/MusicPlayer-Projects/BitChord/shared/src/jvmSharedMain/kotlin/com/music/bitchord/data/spotify/SpotifyLibrary.kt:43). Prefer documented OAuth/PKCE for any approved official integration; Spotify specifically recommends PKCE for mobile apps. [official PKCE](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow).
- Discord presence source explicitly says it uses the user's bearer and identifies as Discord Android. [Discord implementation](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/data/discord/DiscordRPC.kt:11). Discord forbids automating ordinary user accounts outside the OAuth2/bot API. [official Discord policy](https://support.discord.com/hc/en-us/articles/115002192352-Automated-User-Accounts-Self-Bots). Omit this approach from our release plan.
- YouTube API developer policies restrict unauthorized audiovisual downloads/offline storage, scraping and audio/video separation; Google Play IP policy rejects infringement-enabling apps. These official constraints do not prove every local-file or authorized download is disallowed, but they make BitChord's extraction/background-download behavior unsuitable as an assumed Play-ready feature. [YouTube policies](https://developers.google.com/youtube/terms/developer-policies), [Play IP policy](https://support.google.com/googleplay/android-developer/answer/9888072?hl=en).
- Spotify's compliance page lists lyric/video synchronization and DJ/mix uses as disallowed Spotify-platform cases. Keep local-user-file visual/transition features separate from Spotify playback assumptions. [Spotify compliance](https://developer.spotify.com/compliance-tips).

### Inferences

Use a single command/state authority: native player/session owns track, position, queue, focus and output; lyrics/art/downloads consume IDs and state. They must not own a competing player. The visual plane should never route audio through WebView, ExoPlayer or an artwork animation engine.

Keep two clearly labeled listening behaviors: **exact playback** uses source format, same-format gapless and bypass rules; **processed playback** allows native DSP and, later, crossfade/speed/Automix with truthful status. Crossfades, rate changes and overlapping tracks alter samples and cannot be advertised as bit-exact. Changing one setting must cause state, controls and path badges to agree.

No network request, Room query, artwork decode, lyric parse or model analysis belongs inside the native callback/USB pump. Precompute and cache on bounded background workers; send only small immutable updates to rendering/control layers.

### Gaps

- Actual driver compatibility with the FiiO Snowsky Echo and target UAC2/DSP IEM devices was not measured. The donor's code/test support is not our hardware gate.
- No assertion that external endpoints, accounts or providers are currently functional without live authenticated verification.
- Play acceptance, exact rights to individual catalog/media integrations, and distribution licensing need item-level evidence before release, not a blanket conclusion based on project README.

## What licensing choice, phased work and validation should the plan propose?

### Takeaway

Make no license decision on behalf of the user. Recommend independent implementations of selected BitChord features by default, while keeping a separately costed GPL reuse route available. Stage features by dependencies and regression gates, not by donor folder copying.

### Cited Findings

- BitChord root license is GPLv3. GNU explains that incorporating GPL-covered software into a proprietary program is incompatible with GPL distribution and that compatible combined works may be distributed under GPL terms. GPL permits commercial distribution; 'GPL' does not mean 'cannot sell'. [local license](D:/MusicPlayer-Projects/BitChord/LICENSE), [GNU FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#GPLInProprietarySystem), [GNU combination explanation](https://www.gnu.org/licenses/gpl-faq.en.html#WhatDoesCompatMean).
- Root license is not the complete provenance map: `BitPerfectOutput.kt` has an Apache2 header, MixerTransport and USB native driver have LGPL3-only Mornye-derived headers; DST contains LGPL2.1 notice; vendored Signalsmith code is described as MIT. Each selected file and dependency needs its own provenance chain. [Apache header](D:/MusicPlayer-Projects/BitChord/app/src/main/java/com/music/bitchord/playback/audio/bitperfect/BitPerfectOutput.kt:1), [Mornye header](D:/MusicPlayer-Projects/BitChord/app/src/main/cpp/bitperfect/usb_transport.cpp:1), [DST notice](D:/MusicPlayer-Projects/BitChord/app/src/main/cpp/dsd/dst/NOTICE.md), [native dependencies](D:/MusicPlayer-Projects/BitChord/native/third_party/README.md).
- Tests exist across playback exactness, descriptor bounds, DAC volume, source formats, local grouping/order, lyric offset/providers, download sessions and queue windows. Static inventory found 112 files under Android unit tests, 9 shared common test files, 8 shared JVM test files and 8 sharedUi JVM test files; these counts include helper files and do not equal distinct test cases. [USB tests](D:/MusicPlayer-Projects/BitChord/app/src/test/java/com/music/bitchord/playback/audio/bitperfect/usb/UsbAudioLogicTest.kt), [streaming regressions](D:/MusicPlayer-Projects/BitChord/app/src/test/java/com/music/bitchord/playback/audio/DirectAudioStreamingRegressionTest.kt), [queue tests](D:/MusicPlayer-Projects/BitChord/shared/src/jvmTest/kotlin/com/music/bitchord/playback/QueueWindowTest.kt), [lyrics offset tests](D:/MusicPlayer-Projects/BitChord/sharedUi/src/jvmTest/kotlin/com/music/bitchord/LyricsOffsetTest.kt).

### Inferences

Plain-language licensing options for the final plan:

- **Build our own versions of the features:** keep our code and identity, learn the behavior and architecture from references, avoid copying protected donor implementation/assets, and still respect licenses of any third-party libraries/data we choose. This is the recommended planning assumption; it is not a guarantee that a superficial rewrite of copied code removes obligations.
- **Reuse GPL-covered code:** potentially saves selected implementation effort but the distributed combined application usually needs GPL-compatible terms and corresponding-source delivery; account for all contributors and third-party components. A full codebase merger still has major technical cost.
- **Use a separately permissively licensed component:** evaluate it at its original upstream, preserve notices, satisfy all its actual conditions and document modifications. Do not infer that importing one Apache-header file makes its GPL dependencies permissive.

Suggested queue API contract (new design): `playContext(contextId,startEntryId)`, `enqueueNext(trackIds)`, `enqueueLast(trackIds)`, `moveEntry(queueEntryId,beforeEntryId)`, `removeEntry(queueEntryId)`, `setRepeat`, `setShuffle(seed)`, `seek`, `restoreQueue(snapshot)`. Each queue entry has its own ID distinct from track ID, because the same track can appear twice. A generation/revision accompanies asynchronous commands and next-track preparation; edits invalidate affected prefetch/native prepared-next state. Persist queue entry IDs, context, shuffle order/seed and current entry/position with a schema version. The donor's pure QueueWindow is evidence for these needs, not code to transplant by default.

Release-sized recommendation: select one vertical experience first—**browse a real local album → add/reorder queue → play unchanged through current engine → display embedded lyrics/art → enter dock view → stop after track**. This combines the highest-value donor ideas while exercising shared identity, state, clock and lifecycle. Do not promise every web/TV/Wear/party feature as part of the first release.
