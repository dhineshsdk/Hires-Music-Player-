# LastWave-Native donor review

## What is actually implemented?

### Takeaway

LastWave is a substantial Android application with its own Media3/native playback stack, local/offline library, online providers and many utility features. Its best fit is as a donor of bounded features behind the accepted BitChord interface, particularly AutoEQ discovery, container-aware tagging, diagnostics, backup patterns and widgets. This review establishes source presence and architectural behavior, not successful builds or working services.

### Inferences

- LastWave's greatest contribution is functional tooling around an existing player, while importing its screen shell would undermine the user's explicit BitChord UI choice. The bounded donors in the matrix can be adapted without changing which application owns playback.
- Its separate source implementations do not make all features independent modules. Hilt injection, LastWave settings/data classes and its singleton player are adaptation boundaries visible in the cited constructors and playback source.
- Same-rate continuity and double coefficient math do not establish our required bit-exact source bypass or Float64 signal chain; the cited PCM processor explicitly outputs Float32.

### Gaps

- No build, installation, network-provider login, playback, USB hardware or S24+ runtime validation was performed. No claim of bit-perfect output, reliable Automix or working third-party extraction is made.
- No exhaustive duplicate-code or commit ancestry comparison against BitChord/Cubic/Metrolist was performed. This source snapshot does not supply usable Git history for proving ancestry.
- Cloud Drive/Telegram support was not established in reviewed LastWave paths. Do not replace the target `SeekableSource` plan with an assumption that it exists here.

## What should we reuse and where?

### Takeaway

Keep the accepted full BitChord base and our native engine ownership. After the BitChord/native integration gate, port small, testable LastWave capabilities into that base, starting with Audio Lab headphone profiles and support tooling.

### Inferences

- Do not merge wholesale app manifests, provider secrets, application identity, all dependencies or the native playback stack. A small feature port reduces the number of competing services, schemas and processing chains that must be reconciled.
- Tag-writing comments promise atomic replacement, but `File` staging plus backup rename and rollback attempts do not prove power-loss atomicity across all storage providers. The proposed acceptance tests are necessary before editing user originals.
- Diagnostics must treat recent logs and exception messages as sensitive. No comprehensive redaction implementation was established in the inspected diagnostics code.
- AutoEQ data handling remains a release gate: maintain per-profile source/rig/target/version/license metadata and clear the specific intended distributions; offer user-supplied preset import while that work is unresolved. This is a rights/provenance proposal, not a legal conclusion that all AutoEQ data is prohibited.
